# Audio 原理文档

本文档解释Audio子系统在Qualcomm Linux BSP体系里管什么、为什么要对比它、以及它与相邻主题的分工原理——这是理解`Audio.md`具体差异结论的前置知识,不涉及QLI1.0/QLI2.0具体差异结论(结论见`../Audio.md`)。

## 1. Audio子系统管的是哪一段信号链

一条完整的音频信号链自上而下是:应用层音频API → 框架层(图管理/路由抽象)→ 音频服务器(混音/策略)→ 校准数据(ACDB,决定各硬件通路的增益/滤波参数)→ 内核驱动(把数据真正推给ADSP/编解码器硬件)。Audio子系统本文档管的正是这整条链路本身"怎么处理音频信号",不管音频数据"通过什么物理/协议通道被传输出去"——这是理解下面分工原理的关键前提。

Qualcomm的音频架构历史上就是AudioReach(PAL/AGM)血统:QLI1.0虽然用的是`meta-iot-audio`这个内部专有层,但其`SRC_URI`指向的本地源码树本身已经是PAL(Platform Abstraction Layer)/AGM(Audio Graph Manager)架构,只是以"内部源码树整体拷贝编译"的方式集成,并未对外公开。这意味着QLI1.0→QLI2.0在架构层面不是推倒重来,而是同一套设计思路换了一种分发方式。

## 2. 为什么要对比这个主题

音频子系统是本次审计里"专有厂商中间件→标准开源社区栈"最彻底的案例之一:框架层从内部树变为独立开源顶层layer(`meta-audioreach`),音频服务器从PulseAudio切换到PipeWire/WirePlumber,ACDB调优数据本身也从闭源recipe变为公开GitHub仓库。这类转变带来两类现实工程后果:一是API/工具链断裂面——任何依赖PulseAudio特定接口(蓝牙音频策略、AVRCP/A2DP offload路径)的上层应用都需要重新适配;二是供应链与合规问题——调优数据公开发布,需要重新评估是否存在客户专属参数被无意公开的风险。对比的目的正是把这条链路上"哪些环节真的换了标准件、哪些环节名义开源但实质仍是专有交付"逐段厘清,而不是用一句"开源了"笼统概括。

## 3. 与相邻主题的分工边界原理

- BT主栈架构(Fluoride vs BlueZ5)及BT侧A2DP/AVRCP/SCO传输协议本身归WiFi_BT——因为"声音数据本身怎么处理"和"声音数据通过哪条无线协议传出去"是信号链上两个独立的环节,音频服务器只是这条传输通道的上层消费者,不负责实现传输协议本身。
- 音频硬件描述符的device-tree overlay合并机制归Overlay——因为"某个硬件节点的设备树描述怎么被合并进最终产物"是一个跨子系统的通用构建机制问题(与显示、相机的techpack overlay走的是同一套`do_merge_techpack_dtbos`路径),不是音频信号处理本身的技术差异,机制本身只应在Overlay一处讲清楚。
- 内核`.config`层`CONFIG_SND_SOC_QCOM`/LPASS宏驱动等通用内核功能域扫描归Kernel_Build——因为那是"内核配置里有没有打开某个宏"这一构建期通用核查动作,横跨多个子系统(不止音频),不应在每个子系统文档里各自重复一遍同样的扫描方法。

判断原则:**信号链本身怎么处理/播放归本主题,信号数据的物理/协议传输通道、设备树合并机制、内核配置的通用扫描方法各归专属的横向文档**——这条原则的落脚点始终是"这件事是不是音频独有的,还是多个子系统共享的通用机制",共享的机制只在它的专属文档里讲一次。
