# Kernel_Code_Architecture 原理文档

本文档解释Kernel_Code_Architecture在Qualcomm Linux BSP体系里管什么、为什么要对比它、以及它与相邻主题的分工原理——这是理解`Kernel_Code_Architecture.md`具体差异结论的前置知识,不涉及QLI1.0/QLI2.0具体差异结论(结论见`../Kernel_Code_Architecture.md`)。

## 1. 本主题管的是"代码血统",不是"功能达标"

内核代码可以从两个完全独立的维度审视:一是"这段代码是从哪来的、和谁同源、经过了什么治理流程"(代码血统),二是"这个具体驱动的功能好不好用、够不够完整"(功能达标)。Kernel_Code_Architecture本文档管的是前者——两代内核源码的仓库治理模式(单一仓库 vs 多仓庭院式结构)、版本与获取机制(整树拷贝 vs bitbake原生fetcher)、GKI vendor-hook基建存废、commit标签体系,以及基于git历史/文件级diff的同源性判断本身。任何具体驱动"功能是否达标"这类判断,都留给对应子系统文档处理。

内核代码血统天然是分层的:最底层mainline Linux代码可能高度同源,中间层(如Android GKI vendor-hook基建)可能完全分叉,仓库治理主体（是否走Google ACK Gerrit评审还是Qualcomm官方GitHub)又是另一层独立的事实。这三层可以各自呈现不同的同源/分叉状态,不能用一句笼统的"同源"或"分叉"去概括——这正是本主题需要按层拆开分析,而不能只给一个整体结论的原理依据。

## 2. 为什么要对比这个主题

下游团队判断"某个具体内核改动能不能复用/移植"之前,必须先确定这个改动属于代码血统的哪一层:如果是最底层mainline代码,复用风险低;如果涉及Android GKI vendor-hook机制,则两代内核在这一层已完全分叉,不能直接套用。commit标签体系的变化(`ANDROID:`/`UPSTREAM:`→`FROMLIST:`/`BACKPORT:`/`QCLINUX:`)同时揭示了工程方法论的转变:QLI2.0把定制改动尽量推向"先投上游、走内核commit"的方向收敛,这意味着追踪一项定制改动的方法也要跟着变——不能只看Yocto层patch目录,必须去看内核git log的标签历史。这是本主题存在的核心价值:给下游一套"按层判断复用风险"的方法,而不是一个笼统的相似度百分比。

## 3. 与相邻主题的分工边界原理

- 各子系统(WiFi_BT/Camera/Graphics/Display/Audio)具体内核驱动的功能与承接细节各归对应文档——依据上文"代码血统 vs 功能达标"的划分,本主题只回答"这个驱动收到的代码血统是什么样的",不回答"这个驱动好不好用"。
- SELinux/内核安全策略、dm-verity/AVB等内核完整性校验机制归Security_Architecture——因为那是"内核提供的安全能力",与"内核代码本身怎么来的"是不同问题,即便两者都涉及内核这同一份代码。
- 内核外置模块编译框架、模块黑名单、dts/dtb具体编译任务归Kernel_Build——因为那是"怎么把内核编译出来"的构建机制问题,不是"内核代码从哪来、和谁同源"的血统问题。
- 内核补丁全量统计口径归Patch_Management——因为补丁数量统计是一个独立的度量口径问题(涉及src/层与poky/层各自统计范围的纠偏),不是血统判断本身。

判断原则:**内核代码从哪来、和谁同源、经过什么治理流程,归本主题;某个具体功能域的驱动能力、内核安全机制、构建机制、补丁统计口径,各归专属文档**——这与本轮其他主题共享的分工哲学一致:同一份代码可以被不同视角反复分析,只要每个视角回答的问题不同,就不构成重叠。
