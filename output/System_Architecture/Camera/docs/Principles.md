# Camera 原理文档

本文档解释Camera子系统在Qualcomm Linux BSP体系里管什么、为什么要对比它、以及它与相邻主题的分工原理——这是理解`Camera.md`具体差异结论的前置知识,不涉及downstream(maili)/QLI2.0具体差异结论(结论见`../Camera.md`)。

## 1. Camera子系统管的是哪一段链路

一条完整的相机链路自下而上是:ISP内核驱动(把传感器原始数据接进系统)→ CamX/ChiCDK算法引擎(去噪/自动曝光/多摄融合等图像处理算法)→ 相机服务层(向应用暴露统一接口、管理多路摄像头资源)→ 参考App/测试工具。Camera本文档管的是这整条链路"本身怎么处理图像",以及机器人SDK新增的相机组件与EVA计算机视觉分析引擎(一条相邻但独立的能力,专门做视觉分析而非图像采集/呈现)。

CamX/ChiCDK这类核心图像处理算法在两代之间都保持专有闭源,这不是缺陷,而是相机ISP调优本身涉及大量传感器专属的、需要现场标定的经验数据,行业内普遍以专有二进制形式交付——对比的重点不在"是否开源",而在"专有交付的形态本身发生了什么变化"(本地源码树整体编译 vs 按板级下载预编译二进制),这直接决定了下游能否自行调优或只能等厂商出包。

## 2. 为什么要对比这个主题

相机子系统同时涉及三类工程后果:一是可定制性——从"全量源码本地可改"变为"预编译包按板级硬绑定",自定义传感器模块需要厂商重新出包;二是能力缺口——EVA计算机视觉分析引擎在QLI2.0侧的用户态软件栈完全消失,机器视觉能力转向ROS2通用感知栈,这对依赖旧架构计算摄影能力的场景是实质性缺口;三是标定/认证覆盖——Snapdragon Camera参考App消失后,量产标定/ITS认证的等效工具链尚不明确。这些都是"专有→标准化"过程中容易被一句话概括掉、但实际影响产品交付节奏的细节,是本主题存在的价值。

## 3. 与相邻主题的分工边界原理

- AOSP libhardware/camera-metadata HAL适配层的详细取证过程归Layer_Architecture——因为这是跨子系统通用的AOSP适配层机制(其他子系统的HAL迁移可能面对同一套适配层问题),不是相机专属的技术差异,机制本身只应讲一次。
- EVA/CVP两轮纠错涉及的CTA/SV测试工具、TUI、ss-mgr等其他计算机视觉/安全相邻能力的完整取证叙述归Layer_Architecture——因为这些是EVA周边生态的横向能力,不是相机图像链路本身。
- camerastack/xr/vnm/host等产品变体分发机制(`x-ship`标签体系、CRM variant机制)归HY11_HY22——因为"一份代码怎么被分发到不同产品线"是跨子系统的通用产品管理机制,不是相机技术本身的差异,相机文档只承接"这个分发机制具体绑定了哪些相机组件"这一结果,不重复分发机制的实现细节。

判断原则:**图像处理链路本身的技术差异归本主题;跨子系统通用的HAL适配层、产品变体分发机制等"载体"归各自的横向文档**——这与其他System_Architecture子系统文档共享的分工哲学一致:凡是可能被多个技术领域复用的机制,归横向文档一次讲清楚。
