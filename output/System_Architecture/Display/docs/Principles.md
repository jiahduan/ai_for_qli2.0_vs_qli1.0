# Display 原理文档

本文档解释Display子系统在Qualcomm Linux BSP体系里管什么、为什么要对比它、以及它与相邻主题的分工原理——这是理解`Display.md`具体差异结论的前置知识,不涉及QLI1.0/QLI2.0具体差异结论(结论见`../Display.md`)。

## 1. Display管的是"合成"这一层,不是"渲染"

图形管线大致分两个阶段:渲染(GPU把一帧图像的每个像素算出来)与合成(把多个图层——应用窗口、状态栏、视频叠加层等——按顺序叠加输出到屏幕,处理分辨率转换、色彩管理、多显示器分配等)。Display子系统本文档管的正是"合成"这一层——显示合成服务层(SDM Composer/HWC专有栈 vs 标准DRM/KMS+Wayland/Weston)与图形栈整合方式,GPU内部如何把像素算出来不属于这里。

历史上手机/嵌入式平台的合成层普遍由芯片厂商提供专有中间件(如Qualcomm的SDM/HWC),原因是合成阶段往往需要利用芯片专属的硬件合成offload能力(把部分合成工作交给专用硬件而非GPU,以降低功耗)。这类专有中间件天然难以被标准Linux桌面生态(DRM/KMS)直接复用,因此"专有合成栈→标准DRM/KMS+Weston"这类迁移在嵌入式Linux领域是一类典型的架构决策,而不是Qualcomm独有的现象。

## 2. 为什么要对比这个主题

SDM/HWC整套专有栈在QLI2.0侧被整体移除,是本次审计"专有厂商中间件→标准开源合成栈"最彻底的架构转变之一,现实工程后果集中在"能力覆盖是否对等"这一问题上:硬件合成offload、QDCM色彩管理/HDR tone-mapping、并发多显示拓扑、动态刷新率切换等SDM/HWC特有能力,在标准DRM/KMS+Weston体系里未必有直接对应组件。对比的价值不在于评判"开源栈是否更差",而在于给出一份具体的、按硬件事实核实过的能力缺口清单,供下游判断新栈能否覆盖实际硬件配置(例如某机型是否真的是多显示输出,而不是想象中的单一输出)。

## 3. 与相邻主题的分工边界原理

- GPU内核驱动(kgsl)与用户态3D渲染驱动的专有交付形态、GBM厂商实现细节、GPU代际支持细节归Graphics——分工依据正是上文"合成 vs 渲染"这一图形管线阶段划分:合成层消费渲染结果,但不负责渲染本身如何实现。
- 内核态DRM/MSM驱动(`drivers/gpu/drm/msm/`)的commit级同源统计归Kernel_Code_Architecture——因为那是从代码血统/仓库治理角度统计谁改了什么、改动是否同源,不是从"合成能力是否对等"的角度看问题,两者是完全不同的分析维度,即便涉及同一份代码。
- display/mm-devicetree overlay dts的构建与合并机制归Overlay——因为"叠加层(overlay)"这个词在设备树语境下指的是启动期硬件描述的合并机制,与显示合成语境下的"硬件overlay/plane"(合成阶段的硬件层叠加能力)是同名不同物,必须先说清楚这一点再谈归属,以免读者被词汇误导后到错误的文档里找答案。

判断原则:**同一个名词(overlay)在不同技术层面指向完全不同的机制时,分工必须先辨明"层面",再决定归属**——这条原则与Overlay.md开篇的声明相互印证,是本轮9个主题里对"避免同名不同物混淆"表述最直接的案例。
