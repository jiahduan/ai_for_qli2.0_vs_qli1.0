# WiFi_BT 原理文档

本文档解释WiFi_BT主题在Qualcomm Linux BSP体系里管什么、为什么要对比它、以及它与相邻主题的分工原理——这是理解`WiFi_BT.md`具体差异结论的前置知识,不涉及QLI1.0/QLI2.0具体差异结论(结论见`../WiFi_BT.md`)。

## 1. WiFi_BT管的是两条连接技术线各自的完整软件栈

WLAN与BT是两条相对独立的无线连接技术线,各自有自己的驱动、平台守护进程、固件、应用层协议栈(wpa_supplicant/hostapd,或BT主栈)与认证测试工具。WiFi_BT本文档把两条线放在一篇文档里对比,是因为它们在这次架构迁移中经历了同一类型的转变——从芯片厂商专有驱动/协议栈整体切换为主线开源实现(WLAN: QCACLD/Prima→ath10k/11k/12k mac80211;BT: Fluoride→BlueZ5),放在一起对比能更清楚地看出这是一次跨越两条技术线的、同一方向的架构决策,而不是两个孤立的局部调整。

无线连接技术线的另一个特点是天然带有外部认证属性:Wi-Fi联盟认证、Bluetooth SIG认证、射频法规(FCC/CE)测试是这个领域特有的、其他子系统很少遇到的合规负担,这也是为什么对比这条线时必须格外关注"驱动栈切换是否等价于认证资质需要重新走一遍"这类问题。

## 2. 为什么要对比这个主题

驱动栈(CLD/Prima→ath1xk)、芯片族、主机蓝牙栈(Fluoride→BlueZ)三者同时切换,理论上意味着此前积累的认证资质、量产测试SOP(如Sahara固件下载、WLAN FTM工厂测试模式)都可能需要重新验证或寻找等效工具,这是本次审计里认证/合规风险最高的一项。对比的价值在于把"哪些工具/协议/认证真的没有等效物"与"哪些只是换了实现方式但功能等价"分开,给产品/合规团队一份可执行的核实清单,而不是笼统地说"驱动换了、需要重新认证"。

## 3. 与相邻主题的分工边界原理

- DIAG协议栈/`diag-router`与`libdiag`的整体架构对比归Log_System——因为诊断日志路由是横切的日志基础设施,服务的不止WLAN/BT,是所有子系统共享的诊断通道,WiFi_BT只承接"WLAN/BT这条线具体依赖诊断通道的哪些能力(如Sahara固件下载协议)是否有等效物"这一结果,不重复诊断路由机制本身。
- 内核驱动层ath10k/11k/12k vs QCACLD的代码血统本身归Kernel_Code_Architecture管辖范围,本文档已核实关键字在该文档零命中、不重叠——这条边界依据"代码血统"与"驱动功能/产品链路挂接情况"两个不同视角的划分(与Kernel_Code_Architecture原理文档所述一致):本文档关心"哪个驱动栈真正被产品挂接使用",不关心这些驱动代码本身的commit历史。
- 认证合规重新认证的影响判断由本文档承载,不归Security_Architecture——因为这里的"认证"特指产品级Wi-Fi联盟/Bluetooth SIG外部认证流程,与Security_Architecture讨论的SELinux访问控制策略是完全不同的"认证/安全"含义,不能被表面词汇混淆。

判断原则:**看似都叫"认证""安全""诊断"的词,要先分辨它具体指的是哪一层机制,再决定归属**——这与Security_Architecture原理文档强调的"安全大范畴需按机制类别分工"是同一条原则的另一次应用。
