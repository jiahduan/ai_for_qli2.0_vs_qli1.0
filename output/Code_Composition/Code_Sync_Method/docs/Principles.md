# Code_Sync_Method 原理文档

本文档解释"代码同步机制"在多仓协作体系里管什么、为什么repo到kas的切换值得单独作为一个对比维度——是理解`../Code_Sync_Method.md`具体差异结论的前置知识,不涉及QLI1.0/QLI2.0具体差异结论本身(结论见该文档)。

## 1. 代码同步机制管的是什么

多仓工程要解决一个基础问题:"开发者/CI机器怎么从零把这N个仓库的正确版本拉到本地,并让bitbake知道该加载哪些层?"这个问题天然拆成三个子任务:

- **拉取**:把远端N个仓库的代码搬到本地。
- **锁定**:确定每个仓库该停在哪个commit/版本,保证不同机器拉到的是同一套代码。
- **层清单生成**:告诉bitbake"这次构建要加载哪些`meta-*`层",即生成`bblayers.conf`。

repo工具和kas都是为了解决这三件事而存在的工具,但设计取向不同:repo工具源自Android多仓协作场景,核心抽象是"manifest XML描述一组project+revision";kas源自Yocto/OE社区,核心抽象是"YAML描述repos+机器/发行版组合"，天然贴合bitbake的"layer+machine+distro"三元组语义。

## 2. 为什么这个维度的差异会带来现实后果

同步工具的选型不是纯粹的口味问题,它决定了几件实际工程后果:

- **元数据是否内聚**:如果"拉哪些代码"(manifest/repos清单)和"怎么配置bitbake层"(bblayers.conf)是两份分开维护的信息,就存在"手工同步、容易漂移"的结构性风险——这与工具好坏无关,是"信息源是一份还是两份"这个设计选择的直接后果。
- **锁定与复现的绑定强度**:锁定commit的机制如果和层清单生成是同一套YAML驱动,那么"复现一次历史构建"这件事就不需要额外的人工核对步骤;如果锁定信息(manifest revision)和层配置(如手写脚本生成的bblayers.conf)分离,复现构建就依赖"两份信息恰好同步"这个隐含假设。
- **对私有基础设施的耦合**:同步工具本身是否内建了对特定托管平台/评审系统的假设(如是否默认走公司内网Gerrit),直接决定这条协作链路能不能被原样搬到公开开源场景下运作。

QLI1.0用repo+Gerrit这套面向内部私有基础设施设计的组合,QLI2.0用kas+GitHub这套面向开源协作设计的组合,这正是同步机制差异值得单列对比的原因——它不只是命令行操作习惯的变化,而是整条协作链路对基础设施的假设发生了变化。

## 3. 与相邻主题的分工边界原理

- **与Code_Repository的边界**:同步机制回答"怎么把代码搬到本地、怎么锁版本",仓库存储回答"搬到本地之后代码物理上以什么形式组织"。`base.lock.yml`锁定的具体清单和它的两层结构细节,属于"结果状态"问题,归Code_Repository;"锁定机制存在与否、它在同步流程里起什么作用"属于同步机制本身,归本主题——这也是为什么本文档的《对比范围》明确把"`base.lock.yml`锁定的具体repo清单及两层结构细节"排除给Code_Repository,只保留"集中锁定机制的存在性与作用"。
- **与Patch_Management的边界**:kas的`patches:`字段本身是"声明式跨仓补丁"这一同步流程的一个可选步骤(checkout阶段执行),但"补丁字段语义、消费方patches目录关系"这类补丁机制细节已经超出"怎么同步代码"这个问题本身,归Patch_Management;本主题只在描述完整同步工作流时提及这一步骤存在,不展开。
- **与Branch_Management的边界**:kas`patches:`执行后会在目标仓库产生`patched-<sha>`临时分支,这个分支的命名规则和"是否安全"是分支语义问题,归Branch_Management;本主题只关心"这一步是同步流程的一部分"这个事实。
- **与Code_Submission的边界**:代码评审系统(Gerrit/GitHub PR)是同步之后、合并之前发生的事,理论上和"怎么拉代码"关系不大,但QLI1.0的repo+Gerrit是同一套私有基础设施的两个环节,因此本文档在描述"迁移的代价"时会提及评审系统变化,但具体评审流程规则细节归Code_Submission,不在本主题内展开。
