# HY11_HY22 原理文档

本文档解释"CRM variant标签"这类标签体系在闭源产物分发场景里管什么、为什么它值得作为独立主题拿出来对比——是理解`../HY11_HY22.md`具体差异结论的前置知识,不涉及downstream(maili)/QLI2.0具体差异结论本身(结论见该文档)。

## 1. CRM variant标签解决的工程问题

当一份代码库同时包含开源组件和闭源专有组件、且闭源组件需要按不同客户/交付批次/产品形态分发不同的预编译二进制时,工程上会面临一个具体问题:同一份源码构建出来的产物,哪些文件该打进"给客户A的包",哪些该打进"给客户B的包"?这不是简单的"要不要开源"的问题,而是"同一份闭源代码的不同交付形态怎么被系统性地标记和筛选出来"的问题。

CRM(Configuration/Component Release Management)variant标签就是为回答这个问题而存在的机制:在manifest这类声明式元数据上给每个project打上标签(如`x-ship`/`x-quic-distributable`属性),再用打包脚本按标签筛选,把同一次构建产出的`tmp-glibc/prebuilt`目录内容,分流打包进不同的`prebuilt_<variant>/<target>`目录。这本质是"一次构建、多种交付形态"这个诉求在工程上的具体落地方式之一。

## 2. 为什么这个维度的对比是必要的、不是噪音

CRM variant机制之所以值得单独对比,原因在于:如果QLI2.0确实完全不存在这套标签体系,读者第一反应可能是"闭源产物分发能力消失了",但这个判断需要区分两件本质不同的事:

- **分发机制的具体实现方式**(标签+脚本 vs 组件级远程拉取)是否变了；
- **分发这件事本身的能力**(能不能按需交付闭源二进制)是否还存在。

前者变化不等于后者消失。只有把"标签体系是否存在"和"分发能力是否存在"分开验证,才能得出准确判断——这正是本主题存在的意义:不是单纯确认一个字符串消失了,而是要确认"消失的是标签,还是能力"。

## 3. 与相邻主题的分工边界原理

- **与Layer_Architecture、Patch_Management的关系(非排除,是佐证联动)**:HY11/HY22机制消失,与这两篇文档观察到的"QLI2.0大幅去除闭源专有组件与配套私有分发基础设施"的整体趋势方向一致,但HY11/HY22标签本身的分析——CRM variant机制的功能定位、业务差异、替代分发路径——是一个独立、边界清晰的具体对象,不依附于其他两篇文档展开,因此本主题的《对比范围》"明确排除"为空:这不是遗漏,是因为这个具体标签体系确实不存在被其他文档承接的必要,它本身就是一个自足的分析单元。
- **与Graphics.md/Log_System.md的边界**:闭源预编译产物分发这件事的"通用机制"(组件级远程拉取模式本身)归本主题统一分析;Graphics.md/Log_System.md只在各自领域引用具体recipe(如adreno相关、diag-router)作为佐证,不重复展开通用机制分析。这是"通用机制归一处,具体应用领域各自引用"的分工原则——避免同一个分发机制在多篇文档里被反复分析。
- **判断原则**:凡是"标签/机制本身是什么、怎么运作、演进成了什么"这类通用性问题,归本主题唯一承接;凡是"某个具体领域的某个recipe用没用这个机制"这类具体应用问题,留在该领域自己的文档里简单引用,不深挖机制本体。
