# Source_Code_Structure 原理文档

本文档解释"顶层源码组织形态"(是否存在集中汇聚目录)在多仓工程里管什么、为什么这个维度值得单独对比——是理解`../Source_Code_Structure.md`具体差异结论的前置知识,不涉及downstream(maili)/QLI2.0具体差异结论本身(结论见该文档)。

## 1. "源码获取模式"管的是什么

一个基于Yocto构建的产品,专有/半专有源码（内核、图形栈、安全组件等)最终都要在构建时被recipe引用到。但"什么时候把这些源码搬到本地、搬到哪里"是一个独立于recipe本身的组织决策,存在两种典型模式:

- **预取(pre-fetch)模式**:在构建开始之前,统一用某种工具把全部专有源码一次性拉到一个固定的顶层目录(如`src/`),recipe再通过本地路径引用这些已经落地的源码。
- **按需拉取(recipe-driven fetch)模式**:不存在预先落地的集中目录,每个recipe自带`SRC_URI`/`SRCREV`字段,由bitbake的fetcher在真正构建这个recipe时才去远端拉取,下载到构建系统自己管理的工作目录。

这两种模式的本质区别在于:"源码盘点"这件事的入口是"看一个固定目录"还是"遍历所有recipe的元数据字段"。

## 2. 为什么这个维度的差异会带来现实后果

顶层源码是否集中汇聚,直接影响的是**审计/盘点场景下的工作方式**,而不是构建本身的正确性——不管用哪种模式,bitbake最终都能正确构建出产物。但对于需要"一次性知道这个产品到底包含了哪些专有代码"这类问题的场景(合规审查、出口管制、安全审计、许可证盘点),两种模式的成本完全不同:预取模式下,盘点者只需要遍历一个目录树;按需拉取模式下,盘点者必须理解并遍历所有层的所有recipe文件,才能拿到同等完整的清单——信息没有消失,但信息的可发现性(discoverability)和获取成本发生了实质变化。

这正是这个维度值得单独对比的原因:它不是"代码变多变少了"的问题,而是"用什么代价才能知道代码库里有什么"的问题,这个代价的变化对下游合规/审计团队是直接可感知的工程影响。

## 3. 与相邻主题的分工边界原理

- **与Layer_Architecture的边界**:本主题只回答"顶层是否存在集中源码汇聚目录、两种获取模式各自的组织形态是什么";一旦要追问"某个具体专有组件(如`src/security/securemsm`、`src/mdm-ss-mgr`)在新架构下究竟被哪个新层承接、承接后功能是否完整",这已经是层级归属的逐项核实问题,归Layer_Architecture——本主题的"待确认"节明确不重复展开这类逐项核实,只引用Layer_Architecture已核实的结论。
- **与OTA_Mechanism的边界**:`src/OTA`这个具体子目录到`meta-updater`的整层替换,涉及"OTA机制本身怎么从Android式bsdiff+recovery A/B升级变成OSTree+aktualizr"这类架构原理,已超出"顶层源码组织形态"这个问题本身,归OTA_Mechanism(层归属事实本身归Layer_Architecture,机制原理归OTA_Mechanism)。
- **判断原则**:"专有源码整体的落地方式是集中还是分散"这一组织形态问题,归本主题;"某个具体子目录消失后去了哪个层、那个层内部功能是否等价"这类逐项核实问题,归Layer_Architecture;再往下"那个新层承载的具体机制原理是什么"归各自专题文档。这是一条从"整体组织形态"到"层级归属"再到"机制原理"逐层收窄的分工链条,三篇文档分别站在链条的不同环节上。
