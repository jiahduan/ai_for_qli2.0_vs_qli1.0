# Layer_Architecture 原理文档

本文档解释Yocto"层(layer)"这一组织单元在代码组织体系里管什么、为什么"层的数量/命名/归属方式"值得作为独立维度对比——是理解`../Layer_Architecture.md`具体差异结论的前置知识,不涉及downstream(maili)/QLI2.0具体差异结论本身(结论见该文档)。

## 1. 层是什么、为什么Yocto要用这种组织方式

Yocto/OpenEmbedded的核心组织单元是"层"(layer):每个层是一个独立的recipe/配置/补丁集合,通过`bblayers.conf`里的`BBLAYERS`变量声明"这次构建要加载哪些层"。层机制存在的工程目的是**关注点分离**:BSP相关的东西放BSP层,某个厂商的定制放厂商层,某个产品线的专属配置放产品层,层与层之间通过`.bbappend`/优先级(`BBFILE_PRIORITY`)机制协作而不是互相硬编码依赖。

一个厂商/项目怎么组织自己的层,直接反映了它对"什么该独立、什么该合并、什么该公开、什么该保密"这几个问题的工程决策。层的数量本身不是目标,层的组织方式服务于更底层的诉求:代码复用、团队边界对齐、开源/闭源边界控制。

## 2. 层数量变化为什么不能简单读成"功能增减"

层数从59条降到21条这类数字变化,表面上像是"规模缩水",但层数变化的成因至少有三种性质完全不同的驱动力,必须先分清楚是哪一种,才能判断这个数字变化意味着什么:

- **合并**:多个原本独立的层因为功能相关、边界被重新划定,合并进同一个层——代码/能力本身可能完全没有减少,只是物理位置变了。
- **拆分为独立产品**:原本作为内部子层存在的功能,被提升为独立的顶层开源项目——层数从"总数视角"看是减少了(不再算作子层),但代码规模、能力范围可能不变甚至扩大。
- **真实移除/新增**:某个层对应的能力确实被砍掉了,或者确实新增了此前完全没有的产品线。

只有把这三种驱动力拆开统计,才能回答"层数变化背后,能力到底是变多了还是变少了"这个真正有意义的问题——这也是为什么"层数降幅"和"哪些具体能力找不到映射"必须分开呈现,前者是统计事实,后者才是需要逐项核实的工程判断。

## 3. 目录级命名约定(`-internal`/`-prop`/`-core`)管的是什么

在downstream(maili)的`meta-qti-*`命名体系里,`-internal`/`-prop`/`-core`这类后缀不是随意的命名装饰,而是**目录级的可见性/成熟度约定**:通常用来标记"这部分代码能不能对外/是否是内部专有/是不是核心稳定功能"。这种约定的价值在于低成本——不需要额外的权限系统,靠目录命名规范加人工纪律就能大致划出开源/闭源、核心/测试的边界。它的代价也在于此:一旦这套目录级约定被物理上打散(层被合并、重新命名),原来靠命名约定表达的边界信息就会跟着消失,除非有新的机制(如recipe级LICENSE字段、仓库访问权限控制)接管这个职责。这正是本主题《关键差异》里"命名体系的搬迁比层数量变化更需要下游确认"这一判断的原理基础。

## 4. 与相邻主题的分工边界原理

Layer_Architecture做的是"层级/目录归属层面的普查"——回答"这个层去哪了、层内的recipe名字对应什么、这个层的功能范畴大致是什么"。但一旦某个具体子系统的内部工作原理需要深挖(如WLAN/BT驱动栈细节、Display合成服务、Camera CamX/ChiCDK架构、Audio框架内部机制、SELinux策略规则本身、OTA具体实现),这些"层内部怎么运作"的问题已经超出"层这个组织单元本身"的范畴,应该归各自专题文档。判断原则:**"这个功能被哪个层承载/层是否存在对应物"归本主题;"这个功能内部具体怎么实现"归对应专题文档**——这条原则解释了本主题《对比范围》里长长的"明确排除"列表为什么覆盖了几乎所有System_Architecture下的子系统文档:层架构对比天然会触及每个子系统,但只取"层归属"这一层信息,不重复展开子系统本体分析。
