# Code_Repository 原理文档

本文档解释"仓库存储模型"这一维度在多仓协作体系里管什么、为什么值得单独对比——是理解`../Code_Repository.md`具体差异结论的前置知识,不涉及QLI1.0/QLI2.0具体差异结论本身(结论见该文档)。

## 1. 仓库存储模型管的是什么

一个多仓工程要回答的基础问题是:"代码物理上存在哪里、以什么形式组织?"这与"分支管理"回答的问题(代码处于协作历史的哪个位置)是正交的两个维度——同一份代码可以用不同的存储模型承载,也可以在同一种存储模型下选用不同的分支策略。

存储模型的核心权衡点在于"对象库(object store)的集中程度":
- **集中式**:所有子项目的git对象共享同一个底层存储池,子目录本身不是完整仓库,而是通过某种间接层(如符号链接)指向集中池里的对应部分。Google的repo工具正是这条路线的典型实现——`.repo/project-objects`是这个集中池。
- **分散式(polyrepo)**:每个子项目自己是一份完整、独立、可脱离整体单独使用的git仓库。

这个选择直接决定了后续一系列行为的性质,而不只是"文件放哪儿"这种表面差异。

## 2. 为什么这个维度的差异会带来现实后果

存储模型的集中/分散程度,直接映射到至少三类工程后果:

- **清理操作的爆炸半径**:集中存储下,顶层元数据目录(如`.repo`)一旦被删除,所有依赖它的工作树会同时失效——这是"单点故障"式的风险;分散存储下,删除一个子项目的`.git`只影响它自己,风险是"隔离"的。这不是孰优孰劣的问题,而是运维操作的心智模型完全不同:集中式要求开发者对"顶层目录"保持高度敬畏,分散式要求开发者理解"每层都是独立的清理单元"。
- **对外开源/贡献的门槛**:一个仓库能不能被单独`git clone`并独立使用,直接决定它能不能作为一个独立单元被托管到公开代码平台、被外部贡献者直接提交PR。集中存储模型下的子目录,天然不具备这个能力,因为它离开顶层元数据就是不完整的;分散存储模型下的每个仓库天然具备。
- **版本发布单元的粒度**:集中式天然导向"单一顶层SHA/manifest对应一份完整版本"这种单点式版本定义;分散式则没有这个单点,版本必须靠额外的锁定机制(如显式列出每层的commit)人为收口,复现性完全依赖这套机制是否被严格遵守。

QLI1.0/QLI2.0恰好落在这个谱系的两端,这正是把"仓库存储模型"单列成对比主题的原因——它不是简单的"用了什么工具"的问题,而是直接决定了运维安全边界、开源可行性、版本复现方式这三件工程上很重的事。

## 3. 与相邻主题的分工边界原理

- **与Branch_Management的边界**:仓库存储回答"代码物理上存在哪里、以什么形式组织";分支管理回答"当前checkout出来的代码处于协作历史的哪个位置"。两者常常在同一个具体现象(如`base.lock.yml`)上交汇,但问的问题不同——"锁定文件的两层结构本身怎么组织、锁了哪些repo"是存储组织问题,归本主题;"分支名是否能代表锁定文件里的真实版本"是分支语义问题,归Branch_Management。判断原则是:凡是回答"这一层/这份数据物理上放在哪、由谁承载"的,归本主题。
- **与Code_Sync_Method的边界**:仓库存储模型是"结果状态"(代码此刻以什么形式存在),而代码同步机制是"达成该状态的过程"(用什么命令、什么协议把代码从远端搬到本地)。repo工具的`.repo/project-objects`集中对象库是同步机制(`repo sync`)的产物,但"这个对象库本身的组织方式"是存储模型问题,归本主题;"用什么命令触发同步、锁定粒度、跨仓补丁怎么打"是同步机制问题,归Code_Sync_Method。
