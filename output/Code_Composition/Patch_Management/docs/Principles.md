# Patch_Management 原理文档

本文档解释"补丁管理"在Yocto/OE recipe体系里管什么、为什么补丁数量/组织方式的变化值得单独对比——是理解`../Patch_Management.md`具体差异结论的前置知识,不涉及downstream(maili)/QLI2.0具体差异结论本身(结论见该文档)。

## 1. 补丁在Yocto recipe体系里解决什么问题

任何基于上游第三方源码构建定制系统的工程,都要回答一个问题:"我对上游代码做的改动,怎么以一种可追溯、可维护、可随上游版本升级重新应用的方式记录下来?" Yocto/OE给出的标准答案是recipe级补丁机制:改动以`.patch`文件形式与recipe同目录存放,通过`SRC_URI += "file://xxx.patch"`声明,在`do_patch`任务阶段应用到已解包的上游源码之上。这套机制的核心价值是**把"改了什么"和"改动为什么存在"从一次性的源码修改,变成一份可以脱离具体某次源码checkout、独立审查、独立追踪来源的文件**。

## 2. 补丁数量为什么不能直接当作"定制程度"的度量

补丁数量看起来是一个简单的规模指标,但直接拿两侧的补丁总数做减法比较,极易产生误导性结论——原因在于同一个"补丁总量"数字背后,可能混杂着性质完全不同的东西:

- **真实的功能性定制补丁**:针对目标硬件/产品需求对上游代码的实质改动,这是补丁数量本该衡量的对象。
- **第三方vendored库自带的补丁噪声**:如果整份第三方项目(如某个子模块、某个vendored进来的构建工具)本身携带了它自己的补丁目录,这些补丁与本方定制无关,只是"顺带被算进来"的噪声。
- **构建期materialize产物残留**:构建系统在实际编译时,可能把recipe补丁物化复制到工作目录下(如`sysroots-components`),这类副本不是独立的补丁,只是同一份补丁在磁盘上的多次落地。
- **废弃/未激活的历史备份**:某些目录可能是早已不在当前`bblayers.conf`激活列表里的废弃layer的残留拷贝。

如果不把这四类拆开统计,单纯的"补丁总数"比较会同时低估或高估两侧的真实定制规模——这正是为什么本主题的方法论要求"先确认统计口径"是第一步,而不是先出总数。

## 3. 补丁的"命运"分类——为什么消失的补丁不等于消失的功能

一个补丁在新架构下找不到直接对应物,同样存在多种可能的解释,不能默认为"功能被砍掉":补丁所修复的行为可能已经不再需要(架构变了,问题不存在了);补丁的功能可能被上游主线吸收(patch变成了upstream commit,不再需要下游维护);补丁可能被以完全不同的机制实现(如Yocto层补丁变成了内核仓库里带标签的commit)。判断"消失的补丁"到底属于哪一种,需要针对补丁修复的具体行为做等价性检索(如检索该补丁修复的字符串/配置项是否仍以别的形式存在),而不能只看补丁文件本身存在与否。

## 4. 与相邻主题的分工边界原理

- **与Branch_Management的边界**:kas的`patches:`字段在checkout阶段应用补丁后,会产生`patched-<sha>`这类特殊分支承载"锁定commit+本层私有patch"的合成状态。这个分支本身的命名规则/是否有remote/是否容易被误操作,是分支语义问题,归Branch_Management;"补丁字段怎么声明、补丁文件放在消费方哪个目录、什么阶段被应用"是补丁机制本体,归本主题。
- **与systemd文档的边界**:某个具体补丁修复的行为(如securityfs挂载、dm-verity校验)背后的架构原理(为什么需要这个挂载点、dm-verity怎么工作),已经超出"这个补丁存在/消失"这个事实判断,归systemd专题文档;本主题只回答"这个补丁去哪了、有没有等价替代"。
- **判断原则**:补丁数量统计、补丁物理组织方式、跨仓补丁声明机制本身,归本主题;补丁修复的具体子系统行为原理,归该子系统对应文档。
