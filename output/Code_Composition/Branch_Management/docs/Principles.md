# Branch_Management 原理文档

本文档解释"分支管理"在多仓协作体系里到底管什么、为什么downstream(maili)/QLI2.0在这一维度的差异值得单独拿出来对比——是理解`../Branch_Management.md`具体结论的前置知识,不涉及downstream(maili)/QLI2.0具体差异结论本身(结论见该文档)。

## 1. 分支管理在多仓协作体系里管什么

任何多仓库协作方案都要回答同一个问题:"我现在checkout出来的这份代码,处于协作历史的哪个位置、将走向哪里?"这个问题有两个独立的子问题:

- **状态标识**:当前HEAD对应哪个已知的、可复现的版本?
- **演进轨道**:后续的改动应该提交到哪条轨道上,才能被正确地review、合并、追溯?

不同工具给出的答案落在git对象模型的不同层面:repo工具本身不改变git的分支语义,只是在多仓之上加一层manifest revision做统一调度,天然倾向于"detached HEAD+外部元数据描述状态"这条路线;而直接用具名长期分支(long-lived branch)则是把"状态标识"直接下放到git原生对象(refs)上。这两种路线都能达成"知道自己在哪个版本"的目标,只是把这份知识存放在了不同的地方——一个存在manifest+commit message里,一个存在分支名本身。

## 2. 为什么这个维度值得单独对比

分支管理策略的选择直接决定了三类工程行为的成本:

- **开发者心智负担**:detached HEAD要求开发者理解"我现在不在任何分支上,直接提交会变成孤儿commit",这对不熟悉repo工作流的人是反直觉的;具名分支则复用了绝大多数开发者已有的git习惯。
- **误操作的可恢复性**:分支是否存在、是否有remote、是否受保护,直接决定"改错了能不能恢复"。一个没有remote的本地分支(如kas`patches:`机制自动生成的临时分支)天然缺少"push"这个安全网,风险模式和"有remote但保护规则太松"是完全不同的两类风险,不能混为一谈。
- **准入门槛的落地位置**:同一件事("防止未经审查的代码进入主干")可以落在repo工具的流程上,也可以落在git托管平台(GitHub)的规则引擎上。这两者不是谁更强,而是管控点搬了地方——评估协作机制成熟度时,要看"管控逻辑实际落在哪一层",而不是简单看"是否用了具名分支"这一个表面特征。

downstream(maili)/QLI2.0恰好各自代表了这两条路线的典型实现,这正是把"分支管理"单列成一个对比主题的原因:它不是"git用法差异"这种细枝末节,而是协作模型选型的直接体现。

## 3. 与相邻主题的分工边界原理

- **与Code_Repository的边界**:分支回答"这份代码处于协作历史的哪个位置",仓库存储回答"这份代码物理上存在哪里、以什么形式存在"。`base.lock.yml`这类锁定文件既涉及"分支名是否能代表真实版本"(分支语义层面,归本主题),又涉及"锁定文件本身的两层结构、锁了哪些repo"(存储/组织结构层面,归Code_Repository)——判断原则是:凡是回答"这个标识能不能信"的,归分支管理;凡是回答"锁定结构本身怎么组织"的,归仓库存储。
- **与Patch_Management的边界**:kas的`patches:`机制会产生`patched-<sha>`这类特殊分支,分支本身的命名规则、有无remote、是否会被误操作,是分支语义问题,归本主题;而"补丁字段怎么声明、补丁文件存在哪里、`do_patch`阶段怎么应用",是补丁机制本体问题,归Patch_Management——一个是"机制的物化副产物",一个是"机制本身",两者必然相邻但职责不同。
- **与Code_Submission的边界**:分支保护规则(ruleset)存在与否、覆盖范围是分支管理该回答的问题;但"评审要经过几个人、CODEOWNERS怎么配、CI status check具体检查什么"属于代码提交/评审流程的运作细节,已经超出"分支"这个对象本身的语义范畴,归Code_Submission。判断原则是"规则挂在哪个git对象上"归本主题,"规则运作的流程细节"归提交流程文档。
