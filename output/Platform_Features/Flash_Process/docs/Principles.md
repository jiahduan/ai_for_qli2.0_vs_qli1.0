# Flash_Process 原理文档

本文档解释"首次产线刷机"在设备生命周期里管什么范围、为什么要单独对比——这是理解`Flash_Process.md`Comparison结论的前置知识,不涉及QLI1.0/QLI2.0具体差异结论(结论见`../Flash_Process.md`)。

## 1. Flash_Process管的是什么

设备从"编译产出的固件包"变成"产线上一台可开机的实机",要经过一次性的首次镶像写入:通过特定芯片级协议(如Qualcomm的EDL/Firehose模式)、专用工具(QDL)、以及分区静态资源(GPT/`rawprogram*.xml`/`patch*.xml`)把完整的boot/rootfs等分区写入全新存储介质。这个过程只发生**一次**(或产线返修时重复),对象是"空白/待初始化设备",区别于设备已经在跑之后的增量升级。本主题只管这道"第一次写入"的工序:用什么工具/协议、静态资源怎么产出、有没有配套文档、版本怎么追溯。

## 2. 为什么要对比这个主题

首刷是产线的第一道工序,直接决定量产良率与产能,任何"工具链缺失"或"流程变了"的误判都会造成不必要的产线迁移成本或恐慌。这个主题真正的工程价值在于回答一个问题:**引入OSTree这类新的OTA机制后,产线首刷SOP要不要跟着变?** 如果底层芯片级刷机机制(EDL/Firehose/QDL)本身没有变,那么无论后续用什么升级机制,产线首刷环节都可以保持不变——只有分清"首刷"与"升级"是两条独立路径,才能不被"QLI2.0引入了新的OTA架构"这个表面信息带偏,误以为产线也要跟着大改。

## 3. 与相邻主题的分工边界原理

- **首刷之后设备怎么升级**(差分/回滚/OSTree对象存储机制)不是首刷本身,是完全独立的后续路径,归[OTA_Mechanism](../OTA_Mechanism.md)。原理:首刷解决"从0到1"的问题,OTA解决"从1到N"的问题,两者共享同一套芯片级刷机协议(QDL/Firehose)作为最底层依赖,但触发时机、参与角色(产线 vs 售后/远程)完全不同。
- **分区表本身设计了多少个分区、每个分区用途**是分区规划这件事的实体内容,不是"怎么把镶像写进分区"这个动作,归[Partition_Layout](../../Boot_Architecture/Partition_Layout/Partition_Layout.md)。本主题只把`rawprogram*.xml`/`patch*.xml`/GPT bin当作"刷机要写入的产出物"引用,不展开这些文件里具体分了几个区。
- **kas集中锁定commit的机制**(`base.lock.yml`由`kas lock`如何生成、锁定粒度)是构建工具自身的能力,本主题只把它当作`sec_aus.txt`(版本追溯文件)的对应物提及,不展开锁定机制细节,归[Build_Tools](../../Build_Architecture/Build_Tools/Build_Tools.md)。

判断原则:**"怎么把镶像第一次写进设备"归本主题,"写进去之后怎么继续更新"归OTA_Mechanism,"写的内容里分区怎么划分"归Partition_Layout,"版本锁定工具内部怎么实现"归Build_Tools**。这也是为什么本主题在《对比范围》里特别强调"首次刷机与OTA升级路径的边界(仅确认两者独立,不深入OTA机制细节)"——边界本身就是一条值得单独确认的结论,不是可以省略的免责声明。
