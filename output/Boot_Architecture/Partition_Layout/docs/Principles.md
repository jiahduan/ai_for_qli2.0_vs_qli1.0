# Partition_Layout 原理文档

本文档解释"分区布局"这个主题在启动链/存储体系里管什么、为什么它是安全/升级模型的基础设施,以及"产品形态因素"与"架构选择因素"该如何原理性地区分开——不涉及downstream(maili)/QLI2.0具体差异结论(结论见`../Partition_Layout.md`)。

## 1. 分区布局是什么、管什么

存储介质(UFS/eMMC)上的分区表(rawprogram xml/partitions.conf)定义了固件、内核、根文件系统、各类安全服务分别落在哪个物理/逻辑分区。这不只是"划几块空间"的问题:分区本身携带身份和角色语义——哪些分区是A/B双份(支持无缝切换升级)、哪些分区专门服务某个安全硬件模块(keystore/secretkeeper等只有配了对应分区才能提供硬件隔离的密钥服务)。分区布局是bootloader、OTA机制、安全服务三者共同的"地基"——它们都要读这份分区表才能确定"该往哪写、该从哪读"。

## 2. 为什么要对比这个主题

分区布局差异不是简单的"数量多少",而是决定了两件更本质的事:
- **升级模型的物理可能性**:是否存在OS层A/B分区,直接决定"整分区切换式无缝升级"这条路径在物理层面是否可行;没有A/B分区,升级模型只能走别的路子(如OSTree式单分区内原子部署)。
- **安全服务的可用性边界**:硬件密钥库、防重放计数器一类服务,通常依赖专属分区提供的持久化/隔离存储位置;分区不存在,不代表这些安全能力"变差了",但确实意味着"目前没有落地位置",需要另外找地方实现或干脆搬掉这层依赖。

## 3. 为什么要区分"产品形态因素"与"架构选择因素"

对比两个系统时,如果两侧默认目标硬件本身就不是同一世代/同一产品类别(如手机SoC vs 机器人开发板),分区数量/种类的差异里会混杂两种完全不同性质的原因:一种是"这一代硬件/产品形态本来就不需要那么多分区"(与架构无关,换了任何构建体系结果都类似),另一种是"同样的硬件条件下,这套构建体系主动选择不带上某些分区/能力"(是真正的架构/工程选择差异)。不做区分,容易把"产品形态换代"误读成"架构精简了多少能力"。方法论上的解法是**控制变量**:找一个双侧都覆盖到的相同芯片型号,单独对比这个芯片型号在两套构建体系下的分区布局,把"硬件世代"这个变量锁定,才能看出"架构本身"这一个变量单独造成的差异——这是本主题同芯型号(qrb5165-rb5)对比作为基准线的原理依据,不是随意选的验证方式。

## 4. 与相邻主题的分工边界原理

- **与Bootargs的边界**:dm-verity/AVB完整性校验机制本身"怎么运作、cmdline层面怎么声明"归Bootargs;本主题只清点"有没有对应的安全分区存在"这一静态事实,不重复校验机制的取证。
- **与OTA_Mechanism的边界**:本主题只点出"哪种DISTRO变体切换即可启用meta-updater/OSTree路径"这一分区/配置层面的事实,不深挖OSTree/aktualizr具体如何做原子部署、安全性如何评审——那是运行机制层面的事,归OTA_Mechanism。
- **与Boot_Flow的边界**:启动链阶段划分、UKI签名机制不是分区层的问题,归Boot_Flow;本主题的"底层固件A/B分区"只回答"这些分区是否存在",不回答"它们在启动链哪个阶段被读取、由谁验证"。
